# Verify and close a ChatHat lesson

1. Work from the repository root. Follow AGENTS.md and the completion protocol in docs/codex-lesson-guide.md. Use README.md for navigation, docs/chathat-spec.md for requirements, and docs/chathat-implementation-plan.md for acceptance criteria and sequence. Identify the exact lesson from the latest chat direction, current phase tracker and notes, and actual changes. Phase 01 uses docs/progress-documentation/phase_1.md and docs/progress-documentation/phase-01-notes.md. For later phases, locate the matching files. Use listed lesson order because IDs can be out of sequence. Ask only if the target remains materially ambiguous.
2. Review staged, unstaged, and relevant untracked changes with git status --short, git diff, and git diff --cached. If work was already committed, locate the corresponding commit or range from the chat and history. Search only relevant CODEBASE_MAP.json entries before inspecting actual source and tests. Compare the change with the lesson contract, approved deviations, and prerequisites. Preserve unrelated work and staging. Report blockers with file locations. Changes to implementation or tests require explicit authorization.
3. Run required lesson checks and the regression suite. Check commands.txt, actual Compose files, test configuration and fixtures to verify service names, mounts, image freshness, and isolation. Phase 01's usual pytest command is `docker compose -f compose.yaml -f compose.dev.yaml exec api python -m pytest`. Use containerized pytest and Alembic when available. Confirm any integration test or migration check targets isolated test resources before running it. Use test-db only where the checkout and fixtures verify that target. Never run destructive cleanup, migrations against development or production data, or volume removal as part of verification. Run applicable checks such as git diff --check (including staged changes), quiet Compose config validation, and Nginx checks if the lesson calls for them. Avoid printing resolved secrets. Supplementary checks cannot substitute for required pytest coverage.
4. Compare observed results with the exact acceptance criteria. Keep assistant-run evidence, user-supplied evidence, approved deferrals, and unchecked criteria distinguishable. If a mandatory check fails, is unavailable, or lacks coverage, report the specific gap and leave completion unrecorded. A verified implementation can be recorded separately from its pending paired test lesson. Advance to the next implementation only after the paired pytest lesson passes.
5. When the user requests closeout and verification passes, add or update the lesson's notes entry with decisions, exact commands and observed results, coverage limits, and the next lesson. Mark only the verified tracker row Completed with the local date in YYYY-MM-DD and link its evidence cell to that notes entry. Refresh the progress count, percentage, and any exit criteria newly proved by the evidence. Preserve earlier evidence when updating an entry.
6. Reconcile affected CODEBASE_MAP.json entries with actual source, including relevant untracked files, changed declarations, renames, and removals. Follow AGENTS.md for syntax-aware inspection, declared signatures, exclusions, and validation. Leave matching entries intact. Validate JSON with duplicate-key detection and check path normalization, existence, metadata, declaration accuracy, exclusions, and secret safety. Confirm the tracker link resolves and review the final scoped diff.

Report the lesson ID, closeout status, review findings, check commands and results, updated paths, and immediate next lesson or blocker. Keep this workflow scoped to verification and explicitly requested record updates.
