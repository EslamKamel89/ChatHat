# Verify and close a ChatHat lesson

1. Work from the repository root. Follow AGENTS.md and the completion protocol in docs/codex-lesson-guide.md. Use README.md for navigation, docs/chathat-spec.md for requirements, and docs/chathat-implementation-plan.md for acceptance criteria and sequence. Identify the exact lesson from the latest chat direction, current phase tracker and notes, and actual changes. Phase 01 uses docs/progress-documentation/phase_1.md and docs/progress-documentation/phase_1_notes.md. Phase 02 uses docs/progress-documentation/phase_2.md and docs/progress-documentation/phase_2_notes.md. For later phases, locate the matching files. Use listed lesson order because IDs can be out of sequence. Ask only if the target remains materially ambiguous.
2. Review staged, unstaged, and relevant untracked changes with git status --short, git diff, and git diff --cached. If work was already committed, locate the corresponding commit or range from the chat and history. Search only relevant CODEBASE_MAP.json entries before inspecting actual source and tests. Compare the change with the lesson contract, approved deviations, and prerequisites. Preserve unrelated work and staging. Report blockers with file locations. Changes to implementation or tests require explicit authorization.
3. Review any check results the developer supplies before running commands. Use those results as evidence for the checks they cover and skip rerunning those checks. If a result's scope or checkout is unclear, ask for the missing detail only if it affects closeout. Run only required lesson or regression checks for which the developer supplied no result, unless they ask for a rerun. For commands you run, check commands.txt, actual Compose files, test configuration and fixtures to verify service names, mounts, image freshness, and isolation. Phase 01's usual pytest command is `docker compose -f compose.yaml -f compose.dev.yaml exec api python -m pytest`. Use containerized pytest and Alembic when available. Confirm any integration test or migration check targets isolated test resources before running it. Use test-db only where the checkout and fixtures verify that target. Never run destructive cleanup, migrations against development or production data, or volume removal as part of verification. Consider applicable checks such as git diff --check (including staged changes), quiet Compose config validation, and Nginx checks if the lesson calls for them. Avoid printing resolved secrets. Supplementary checks cannot substitute for required pytest coverage.
4. Compare developer-supplied and assistant-run results with the exact acceptance criteria. Keep assistant-run evidence, user-supplied evidence, approved deferrals, and unchecked criteria distinguishable. If a mandatory check fails, is unavailable, or lacks coverage, report the specific gap and leave completion unrecorded. A verified implementation can be recorded separately from its pending paired test lesson. Advance to the next implementation only after the paired pytest lesson passes.
5. When the user requests closeout and verification passes, add or update the lesson's notes entry with decisions, exact commands when known, results with their source, coverage limits, and the next lesson. Mark only the verified tracker row Completed with the local date in YYYY-MM-DD and link its evidence cell to that notes entry. Refresh the progress count, percentage, and any exit criteria newly proved by the evidence. Preserve earlier evidence when updating an entry.
6. Reconcile affected CODEBASE_MAP.json entries with actual source, including relevant untracked files, changed declarations, renames, and removals. Follow AGENTS.md for syntax-aware inspection, declared signatures, exclusions, and validation. Leave matching entries intact. Validate JSON with duplicate-key detection and check path normalization, existence, metadata, declaration accuracy, exclusions, and secret safety. Confirm the tracker link resolves and review the final scoped diff.

Report the lesson ID, closeout status, review findings, check commands and results, updated paths, and immediate next lesson or blocker. Keep this workflow scoped to verification and explicitly requested record updates.

## Explain answers with realistic data

For any question, lead with the answer in plain language and use one small, realistic example with fictional data. When code is involved, follow the same input through the relevant steps. Show which values or state change, what the caller gets back, and why. If the code only reads a value or rejects an input, show the decision and its effect. Define unfamiliar terms only when needed and keep the explanation to the few steps that make it clear. Treat example values and outcomes as illustrative.

For example, suppose a monitoring service sends `GET /health` while ChatHat is starting. The route checks the app's `started` flag. When the flag is `False`, it returns HTTP 503, so the monitor sees that the app is unavailable. After startup sets the flag to `True`, the same request returns HTTP 200 with `{"status":"ok"}`.
