## P02-I01 · Organization and account data model

Verified on 2026-11-24 against the working tree. The required foreign key on `users.organization_id` represents membership, and global uniqueness applies to canonical account emails. Invitations reference their organization directly and use a composite foreign key to require the issuer to belong to that organization. The checkout adds timestamp fields and ORM relationships and uses an autogenerated Alembic revision. Invitation recipient emails have a length limit. The canonical email constraint applies to accounts, while invitation input handling remains part of P02-I05.

Assistant-run verification:

- Confirmed that the running API container's migration environment and `0002_organization_accounts` revision matched the checkout by SHA-256.
- In a disposable PostgreSQL database on `test-db`, used the repository's `migrate` helper to upgrade from `0001_pgvector` to head. Alembic `command.check` reported no new upgrade operations. ORM inserts persisted an owner and same-organization invitation with generated timestamps. PostgreSQL rejected missing and nonexistent memberships, a duplicate account email across tenants, and a cross-tenant invitation issuer. Downgrade to `0001_pgvector` removed all three new tables and preserved pgvector.
- `docker compose -f compose.yaml -f compose.dev.yaml exec -T api ruff check src migrations` passed. The equivalent `mypy` command found no issues in 20 source files.
- `docker compose -f compose.yaml -f compose.dev.yaml exec api python -m pytest -v` reported 48 passed and 30 deprecation warnings in 3.73s. The suite checked migration upgrade, downgrade and re-upgrade, plus persistence across an isolated test-server restart.

P02-T01 is next and will add dedicated PostgreSQL pytest coverage for uniqueness, foreign keys, one-organization membership, and cross-tenant persistence constraints.
